Pipeline workflow

Run jobs.
Respect dependencies.

Each node is a configured container step. Independent branches can run together; a dependent step waits for every prerequisite to succeed.

Pipeline / example-buildIllustrative states · maxParallel: 2

One fork. Two eligible jobs.

Both test steps depend on build. With two execution slots, they can run together. package remains queued until both succeed.

  1. buildSucceeded
  2. unit-test + policy-testRunning in parallel
  3. packageWaiting for dependencies

A failed branch stops the join.

A step becomes eligible only after all declared dependencies succeed. Configured retries can retry a failing step; exhausted failure prevents this example’s package step from running.

  1. unit-testSucceeded
  2. policy-testFailed
  3. packageBlocked by dependency

Environment promotion

Three Applications.
One pinned revision.

Dev, staging and production have separate Application records and deployment targets. A downstream Application selects the exact Git SHA from its upstream completed Release after fresh evidence and configured verification qualify the candidate.

Before target deployment

Test the upstream environment.

trigger.tests creates a verification Pipeline. Its Jobs run on the management cluster and test the upstream environment before the downstream Release is admitted.

Admission

Hold the reviewed candidate.

With manual sync policy, approval stays bound to the candidate and its deployment settings. A waiting or failed candidate leaves the accepted downstream Release in place.

After target deployment

Observe the new target.

Stage gates check the newly deployed environment. Health and sync observations provide evidence for any later promotion.

A configured promotion chain can use different clusters and namespaces while retaining the upstream Git revision.

Run it yourself

Start on a test cluster.

Self-hosting means selecting a registry image the cluster can pull, installing the Helm chart, and applying a complete Application manifest. Check the active Kubernetes context first.

  1. 01

    Prepare

    Use Kubernetes, kubectl, Helm, Docker and Go 1.26+. Cert-manager is needed only if you enable admission webhooks.

  2. 02

    Install

    Build and push an operator image, pass its tag to the chart, then check the controller pod.

  3. 03

    Apply

    Create an Application from a complete manifest. Inspect its status and the related Release.

Read the setup guideBrowse samples
Self-hosted operatordocumented sequence
git clone https://github.com/paprikacd/paprika.git
cd paprika
kubectl config current-context

# Replace with your registry and immutable tag.
make docker-build docker-push IMG=YOUR_REGISTRY/paprika:YOUR_TAG
make helm-deploy IMG=YOUR_REGISTRY/paprika:YOUR_TAG
kubectl get pods -n paprika-system

# After saving a complete Application manifest:
kubectl apply -f application.yaml

Optional CLI

Inspect with the command line.

The CLI installer downloads a published release archive and verifies its checksum. The CLI is separate from installing the operator. Use your own server address when self-hosting.

install.shverified release archive
Latest published releasecurl -fsSL https://raw.githubusercontent.com/paprikacd/paprika/master/install.sh | sh
Pin a releasecurl -fsSL https://raw.githubusercontent.com/paprikacd/paprika/master/install.sh | PAPRIKA_VERSION=vX.Y.Z sh
Choose a writable destinationcurl -fsSL https://raw.githubusercontent.com/paprikacd/paprika/master/install.sh | PAPRIKA_INSTALL_DIR="$HOME/.local/bin" sh

Copy unavailable? Select the command text and copy it manually.

Platform and integrity

Darwin (macOS) and Linux on amd64 and arm64. The installer checks the archive against the release checksum before replacing the binary.

Version and checksum

Set PAPRIKA_VERSION=vX.Y.Z. Audit the latest published checksums. A pinned release uses https://github.com/paprikacd/paprika/releases/download/vX.Y.Z/checksums.txt.

No implicit privilege escalation

The script never invokes sudo. Set PAPRIKA_INSTALL_DIR to a writable directory; if it falls back to ~/.local/bin, it prints the exact PATH export. Homebrew is not yet supported.

Build from source

Clone the canonical repository and compile the CLI with the pinned Go toolchain.

git clone https://github.com/paprikacd/paprika.git
cd paprika
go build -o ./bin/paprika ./cmd/paprika
