Connect the observability gateway

Configure Paprika Observe providers and authenticated MCP access for querying metrics, logs, traces and saved dashboards.

Maintained with the sourceView source on GitHub ↗

The observability gateway is Paprika's MCP surface for querying observability backends — logs, metrics, and traces — through pluggable connectors. It runs as its own microservice (its own Deployment in split mode, its own --mode in the shared binary) and exposes:

Text
https://<paprika-host>/observe/mcp

on the same hostname and TLS identity as the console (/mcp keeps serving the fleet surface). Gateway tokens carry the paprika-observability audience and the paprika:observe scope for reads. When Insights is configured, the separate paprika:insights:write scope enables saved-query and dashboard authoring, subject to the user's Insights RBAC permissions. A token minted for the console or fleet MCP surface is not replayable here and vice versa — even though all surfaces share the deployment's HMAC token secret.

For request budgets, scope boundaries, repeatable local checks, profiling and live acceptance, see validation guidance.

Architecture

Text
Claude/Codex → https://paprika.example.com/observe/mcp     (HTTPRoute, /observe)
                     │ h2c
                     ▼
       Deployment/<release>-observability-gateway
                     │  mcp.Server (RoutePrefix /observe, ScopeObserve + optional authoring,
                     │  console resource extensions disabled, own embedded
                     │  consent page at /observe/consent)
                     ▼
       internal/observabilitygateway.Backend
                     │  per call: get ObservabilityProvider CR
                     │  (namespace/name) → resolve credentialsSecretRef
                     ▼
       connector.New(type).Query(...)  (stateless; config travels per-request)
                     │
                     ▼
       prometheus / loki / tempo / otlp  (plain HTTP, no vendor SDKs)
  • internal/observabilitygateway/connector — the connector framework: Connector interface (Descriptor / ValidateConfig / Query), a dup-rejecting Registry, signal/state/sentinel vocabulary that deliberately parallels internal/clusterprovider and internal/dataprovider (state strings OK/NotConfigured/NotAvailable/Error/Forbidden; sentinels ErrForbidden / ErrNotConfigured / ErrUnsupported / ErrNotAvailable).
  • Connector errors never echo endpoints, credentials, or response bodies into tool results — users get fixed sentences, detail goes to the gateway log (clusterprovider sanitize discipline).
  • Unsupported query shapes return a StateNotAvailable result plus an error wrapping ErrUnsupported; the backend returns the result and logs the error.

Query backpressure and provider bulkheads

Paprika Observe now admits short bursts through bounded queues instead of rejecting every query when execution is busy:

  • MCP per-principal token buckets (50 requests/s, burst 100) permit up to 8 queued requests per authenticated user and 64 globally, each waiting at most 2 seconds. A canceled MCP call does not execute after disconnect.
  • The observability backend permits 4 concurrent queries globally and 2 concurrent queries per provider, with at most 32 global waiters and 8 per-provider waiters. Admission waits no longer than 5 seconds, while each execution retains its 30-second budget and any earlier caller deadline.
  • Insights permits 16 concurrent query executions and up to 64 queued requests waiting at most 2 seconds. query_dashboard executes distinct saved queries once and propagates the request deadline to providers.
  • Overfull queues still return an explicit capacity error (429 / resource exhausted); holding a connection indefinitely would consume worker memory, create head-of-line blocking and hide provider outages.
  • All limits are per process. Multiple replicas do not provide a single global cluster-wide queue; shared ordering across pods requires a separate durable scheduler, which is not appropriate for synchronous MCP requests.

Query results are returned synchronously. Queuing does not change OAuth scopes, provider RBAC, saved dashboard versions or query timeout/error semantics.

The MCP surface

Fifteen provider tools, all read-only and requiring paprika:observe:

Tool Purpose
list_observability_providers List ObservabilityProvider CRs (name, type, state)
get_observability_provider One provider's descriptor (signals it supplies)
query_logs LogQL query (loki/otlp connectors)
query_metrics PromQL instant/range query (prometheus/otlp)
query_traces TraceQL search or trace_id fetch (tempo/otlp)
query_records Bounded typed rows from Shorted, Uptime or read-only PostgreSQL
list_metric_names Enumerate a metrics provider's metric names (prefix/limit filters)
list_metric_series Bounded metric series/label sets in a time range; supports approximate cardinality inspection
list_label_names Label names — globally or on one metric (prometheus/loki/tempo tags)
list_label_values One label's values, optionally constrained to a metric
get_metric_metadata One metric's type/help/unit (prometheus /api/v1/metadata)
list_trace_services Service names a tempo provider has spans for
list_provider_types The provider-type catalog (library view)
describe_provider_type One type's config schema + onboarding walkthrough
validate_provider Offline syntax validation of prospective provider configuration

Metric, label and trace-service exploration accepts optional RFC 3339 start and end bounds. Series enumeration defaults to the trailing thirty minutes; explicit windows are limited to 31 days. A bounded series sample is not a global active-series count. Insights consumes the supported Prometheus/Tempo tools through this MCP endpoint using the signed-in user's delegated access.

Insights also uses query_records for application and SQL dashboards. These providers can project numeric columns through query_metrics; inventories do not become historical series unless the source supplies timestamps. See the repository example library and the Shorted, Uptime and PostgreSQL adapter contracts.

When Insights is configured, the same MCP endpoint additionally exposes:

Tool Required scope Purpose
list_insights_providers paprika:observe Discover provider IDs used in saved UI documents
get_insights_schema paprika:observe Discover canonical dashboard, widget or saved-query JSON Schema and examples
list_saved_queries, get_saved_query paprika:observe Read saved queries and their ETags
list_dashboards, get_dashboard paprika:observe Read shared dashboards and their ETags
query_dashboard paprika:observe Execute a saved dashboard and read compact, versioned live signals with optional variable overrides
create_saved_query, create_dashboard paprika:observe + paprika:insights:write Create a new shared document without replacing an existing ID
update_saved_query, update_dashboard paprika:observe + paprika:insights:write Update a document using the exact ETag from its latest read
patch_saved_query, patch_dashboard paprika:observe + paprika:insights:write Edit selected fields and dashboard widgets by ID, atomically against the current ETag

All document tools also enforce the user's global insights read/write RBAC. The authoring scope grants no fleet operations or provider configuration. Existing paprika:observe tokens remain read-only, including on refresh; authoring requires a fresh native OAuth grant that explicitly requests the new scope. An omitted-scope authorization request retains the read-only default. Create saved queries before dashboards that reference them, and preserve typed parameters and bindings. A stale update returns a conflict: reread the document and reconcile the intended edit instead of issuing a wildcard overwrite.

Start authoring with get_insights_schema (kind: dashboard, widget, or saved_query). It returns the deployed Insights service's full JSON Schema, examples and semantic-validation notes. For small changes, prefer patch_saved_query or patch_dashboard: nested objects merge, null removes a field, and arrays replace in full. Dashboard widgets use widget_edits with add, update or remove operations addressed by stable widget ID. A batch is validated and persisted once; any invalid edit or ETag conflict leaves the document unchanged. See the targeted authoring contract.

The tools use the same persistent Insights service as the UI. Open workspaces refresh externally saved changes while protecting unsaved local drafts. Provider credentials and the Insights service token never enter tool responses. query_dashboard resolves the same saved-query bindings as the UI and executes identical panel queries once. Its structured result contains latest readings, range summaries, a bounded trace sample, document ETags and explicit missing/error/truncation states. History is opt-in; service overrides never modify saved defaults. Data availability is not a service-health verdict. See the dashboard query contract for limits, examples and interpretation. See the Observe plugin for connection and authoring guidance.

The five exploration tools answer in the backend's own JSON envelope ({"status":"success","data":[...]} for prometheus/loki, {"tagNames":[...]} / {"tagValues":[...]} for tempo) so a caller can explore a backend and then query what it found without learning a gateway dialect.   • Consent: browsers are redirected to /observe/consent, a minimal self-contained page embedded in the gateway binary. Unifying it with the branded console consent page is follow-up work.

Configuring providers

ObservabilityProvider is a namespaced CR (group observability.paprika.io):

yaml
apiVersion: observability.paprika.io/v1alpha1
kind: ObservabilityProvider
metadata:
  name: prometheus
  namespace: paprika-e2e
spec:
  type: prometheus                     # prometheus | loki | tempo | otlp |
                                       # gcp-cloudlogging | gcp-cloudmonitoring | gcp-cloudtrace |
                                       # aws-cloudwatch-logs | aws-cloudwatch-metrics |
                                       # aws-xray | aws-cloudtrail
  config:
    endpoint: http://kube-prometheus-stack-prometheus.monitoring:9090
  # credentialsSecretRef:             # optional
  #   name: grafana-cloud-token       # namespace/key optional (default: CR ns, "credentials")
  • spec.config is opaque per-connector JSON, validated at admission by the connector itself (webhook rejectInlineCredentials refuses literal token/password keys anywhere in the document; put credentials in a Secret).
  • spec.credentialsSecretRef document: nil = no auth; otherwise the secret data[key] is sent as Authorization: Bearer <value>, or HTTP Basic when it contains user:password.
  • The referenced Secret must be labelled observability.paprika.io/credentials=true. The gateway's service account can read far more than provider credentials, and whoever writes a provider chooses both the Secret and the endpoint it is sent to, so only Secrets opted in by label are ever read; any other reference reports NotConfigured. CreateObservabilityProvider labels the Secret it creates; label Secrets you create yourself: kubectl label secret <name> -n <ns> observability.paprika.io/credentials=true.
  • A Secret in another namespace (credentialsSecretRef.namespace) is read only for a caller authorized for providers in that namespace. The status prober acts for no caller, so such a provider reports NotConfigured in status while authorized queries still work.
  • endpoint (absolute http(s) URL) is the one universal config key; unknown keys fail validation (typo fail-fast). Optional keys:
    • headers — map of extra request headers (≤16 entries, ≤4 KiB combined): vendor tenancy like Loki/Grafana/Mimir X-Scope-OrgID. Operator-declared headers win Authorization collisions (documented + tested).
    • insecureSkipTLS — bool, for self-signed in-cluster backends only (never off-cluster; per-config client so verified/unverified TLS sessions never share connection pools).
    • step — prometheus-only range-query step override (Go duration, >0, ≤1h; otherwise derived as max(10s, span/250)).

Config knobs (all optional, bounded): series, pointsPerSeries, labelsPerSeries, logEntries, traces, spansPerTrace (payload shape), latencyMs (context-aware synthetic latency), failEvery (deterministic stable error subset — every Nth distinct query string), seed (deterministic generator seed; identical query + seed = identical data)

Perf testing with the mock connector

hack/obsloadgen drives the gateway's MCP surface with N concurrent clients (one self-signed paprika-observability token each — distinct subjects so the per-subject rate limiter binds no client but its own), and task perf:obs-* wraps the loop for the kind perf stack:

sh
task perf:obs-seed COUNT=50        # seed varied mock providers (idempotent)
task perf:obs-load SECS=60 CLIENTS=32 RPS=5
task perf:obs-profile SECS=30      # combined load + pprof capture
task perf:obs-metrics              # gateway /metrics + kubectl top

Grafana Cloud uses the same three native connectors with the Grafana Cloud endpoint and an API token as credentials, e.g.:

yaml
spec:
  type: prometheus
  config:
    endpoint: https://prometheus-prod-01-us-west1.grafana.net/api/prom
  credentialsSecretRef:
    name: grafana-cloud   # Secret labelled observability.paprika.io/credentials=true

Cloud connectors (GCP and AWS)

The seven cloud connectors share the same CR shape; what changes is the credential document and the config keys:

  • AWS (aws-cloudwatch-logs, aws-cloudwatch-metrics, aws-xray, aws-cloudtrail) — spec.credentialsSecretRef holds the same snake_case JSON the EKS cluster provider accepts: {"access_key_id": "...", "secret_access_key": "...", "session_token": "..."}. Omit the ref entirely to use the ambient SDK chain (IRSA / IMDS / environment). Config keys: region (required), plus the connector's required selector (logGroup for logs, namespace for metrics), plus optional endpoint (VPC endpoints / in-cluster emulators — the SDK sends to it verbatim) and insecureSkipTLS.
  • GCP (gcp-cloudlogging, gcp-cloudmonitoring, gcp-cloudtrace) — the secret holds a Google credential JSON restricted to service_account, external_account or impersonated_service_account (type-checked before loading, same as the GKE cluster provider); omit it for ambient identity (GKE Workload Identity / metadata server). Config keys: optional projectId (defaults to the credential's project), optional endpoint (private proxies / fakes — replaces the *.googleapis.com base), insecureSkipTLS.
    • Ambient identity is the gateway's own, so it is sent only to an https *.googleapis.com endpoint with TLS verification on. A provider with no credential Secret and any other endpoint, or insecureSkipTLS, reports NotConfigured and sends nothing; give such a provider its own credential Secret.
    • In external_account and impersonated_service_account documents, token_url, token_info_url and service_account_impersonation_url must be https *.googleapis.com URLs, universe_domain must be empty or googleapis.com, and credential_source.executable is refused. These fields decide where x/oauth2 posts subject and access tokens; it does not validate them itself.

Empty connector queries are used internally for small health reads. Prospective validate_provider and the console's Validate configuration action only check syntax and never send credentials or make backend requests. Establish connectivity by querying an approved provider with explicit bounds.

E2E coverage runs in kind: LocalStack serves CloudWatch Logs + Metrics (X-Ray and CloudTrail are license-gated there, so those two run against a canned nginx responder), and a JWT-issuing nginx fake serves the GCP REST shapes with a runtime-generated service-account key — see test/e2e/observabilitycloud_test.go.

Enabling the gateway

Check the installed release and source chart versions before upgrading the main release. When the installed chart is newer, use the separate gateway-only Helm add-on to preserve its controllers and resources. Its render-only helper emits three resources and keeps public routing disabled unless explicitly requested and approved.

sh
helm upgrade paprika-e2e charts/chart/ \
  --namespace paprika-e2e --values deploy/test-values.yaml \
  --values deploy/omega-values.yaml \
  --set observabilityGateway.enabled=true --wait --timeout 5m

Preconditions enforced at render time (helm template fails otherwise): deploymentMode: split, auth.enabled, a non-empty PAPRIKA_AUTH_TOKEN_SECRET via observabilityGateway.extraEnv(From), and mcp.publicURL. A preconfigured OAuth client is optional for the gateway: leave both mcp.oauth.clientId and mcp.oauth.redirectUris empty for dynamic registration only, or provide both for an approved static client. Partial configuration is rejected. Rendering and DCR-only startup configure no persistent client; native OAuth sign-in and client-access approval are separate actions. The shared mcp configuration fields do not require mcp.enabled: that switch controls the independent fleet MCP surface and may remain disabled. Public exposure reuses the api-server's Gateway/hostname:

yaml
observabilityGateway:
  enabled: true
  ingress:
    enabled: true     # HTTPRoute: path prefix /observe → gateway Service

Verify:

sh
curl -s https://paprika.benebsworth.com/.well-known/oauth-protected-resource/observe/mcp | jq .
# { "resource": "https://paprika.benebsworth.com/observe/mcp",
#   "authorization_servers": ["https://paprika.benebsworth.com/observe"],
#   "scopes_supported": ["paprika:observe", "paprika:insights:write"] }
# The authoring scope is present only when Insights is configured.

For providers signed by a CA outside the system trust bundle, configure observabilityGateway.additionalCACertificates as a map of .crt or .pem filenames to public PEM CA certificates (one certificate per file). The chart creates a ConfigMap, mounts it read-only at /etc/paprika/additional-ca-certificates, and includes its contents in the gateway pod checksum so certificate updates roll out automatically. This is gateway-wide trust for all its connectors; include only CAs approved for that scope. Provider hostname verification remains enabled.

SSL_CERT_DIR includes /etc/ssl/certs, /etc/pki/tls/certs, and the added directory. The default system certificate file is unchanged. Do not also set SSL_CERT_DIR in observabilityGateway.extraEnv; the chart rejects ambiguous configuration. Private keys and provider credentials belong in their existing Secret references, never in this public certificate map. Omitting the map leaves the gateway's default trust configuration unchanged.

Autodiscovery from in-cluster Services

Backends running in the same cluster can register themselves without anyone hand-writing provider YAML. The provider-discovery controller (internal/controller/observe) watches Services carrying the opt-in annotation and materializes each as an ObservabilityProvider CR in the Service's namespace. It runs in the observability gateway pod itself (a dedicated controller-runtime manager alongside the MCP server, single replica with leader election off), so discovery works even where only the observability microservice is installed; the pipeline manager also registers the reconciler, and dual-running converges safely:

yaml
metadata:
  annotations:
    observability.paprika.io/discover: "true"

Type and endpoint are inferred from the Service: the connector type comes from the Service name (prometheus, loki, tempo, otel substrings — so prometheus-operated, loki-gateway, tempo-query-frontend, and otel-collector all just work), the port from each type's well-known port names (http-web/web/http, http-metrics, otlp-http, …) falling back to the first declared port, and the endpoint is http://<service>.<ns>.svc:<port>. Inference overrides:

Annotation Effect
observability.paprika.io/type explicit connector type (prometheus/loki/tempo/otlp) when the name matches nothing
observability.paprika.io/port explicit port number (invalid values hard-reject the Service)
observability.paprika.io/path base path appended to the endpoint (e.g. Prometheus behind /prometheus)

Ownership rules keep the CR-as-system-of-record invariant:

  • Discovered CRs are labeled observability.paprika.io/discovered: service and owned by the Service — deleting the Service or removing the annotation garbage-collects the provider.
  • The controller converges type/endpoint drift on labeled CRs but never touches a CR without the label — dropping the label from a discovered provider hands it to the operator permanently, and an operator-written CR of the same name is never deleted or modified.
  • Discovered providers have no credentials (in-cluster backends are usually unauthenticated); edit the CR to add credentialsSecretRef (to a labelled Secret) and it still converges endpoint changes around your edit.

Example — everything kube-prometheus-stack + loki + tempo need:

sh
kubectl annotate svc prometheus-operated -n monitoring observability.paprika.io/discover=true
kubectl annotate svc loki-gateway -n monitoring observability.paprika.io/discover=true
kubectl annotate svc tempo-query-frontend -n tracing observability.paprika.io/discover=true
kubectl get observabilityproviders -A

Provider status

The gateway is also the writer behind the provider board's STATE column: its status prober re-runs the catalog's per-type health probe — the cheapest read each backend accepts, the same probe the onboarding wizard's Test connection runs — against every registered provider on --obs-provider-probe-interval (chart observabilityGateway.probeInterval, default 5m; 0 disables status writes) and patches the verdict onto each CR's status: state (OK/NotConfigured/NotAvailable/Error/ Forbidden), a fixed-sentence reason that never carries credential or endpoint detail, observedGeneration, and a Ready condition mirroring the state. The probe resolves credentials through the same path a query does, so status shows what a query would experience right now; kubectl get observabilityproviders and the console's provider board read the same fields.

Managing providers in the console

The dashboard's Observability page (/dashboard/observability/, listed under Sources in the sidebar) renders three boards:

  • Provider library — every provider type the gateway can connect to (OSS + GCP + AWS), served from the gateway's catalog: vendor, category, signals, and a one-line summary per type.
  • Providers — every ObservabilityProvider (name, type, signals, endpoint, state, discovery provenance). Discovered providers carry a DISCOVERED pill; states map to the console's status tones.
  • Tool usage — per-tool call/error counters maintained by the gateway's usage tracker and served from its authenticated /observe/api/usage endpoint. The api-server proxies it over GetObservabilityUsage (minting a short-lived paprika-observability token per call); when the gateway is not deployed the board renders the canonical "not configured" sentence instead of zeros.

Selecting Set up on a library card opens the onboarding wizard. Its Validate configuration action calls ValidateObservabilityProvider for offline syntax checks and does not establish backend access. Create provider is a separate administrative operation that creates the provider CR and, when explicitly supplied through the secure administration flow, its credential Secret. Creation requires the console's write action on observabilityproviders in the target namespace. Workload identity avoids a static credential document.

The same data is available programmatically: PaprikaService.ListObservabilityProviderTypes, GetObservabilityProviderType, ValidateObservabilityProvider, CreateObservabilityProvider, ListObservabilityProviders, and GetObservabilityUsage. On the MCP surface, agents get list_provider_types, describe_provider_type, and validate_provider alongside the query tools.

Linking providers to Applications (future)

The v1 CRD is deliberately shaped for a follow-up binding CR (DataProviderBinding-style scope precedence: application > namespace > cluster) that will attach providers to Applications so the console view layer and deployment pages can surface logs/metrics/traces per app. The gateway itself is agnostic to that: tools already accept any namespace/name provider.

Dashboard and query integration

Paprika Insights consumes the same authorized provider backend as the MCP tools. The gateway exposes GET /observe/api/providers, POST /observe/api/query and POST /observe/api/explore for this integration. These routes require an Observe-audience bearer token and paprika:observe, then enforce the caller's namespace RBAC before reading providers or credential Secrets. HTTP and MCP requests share the connector concurrency budget and bounded response limits.

The query route accepts a canonical namespace/name provider, signal, native query, RFC3339 start/end, optional stepSeconds, limit and supported pagination fields. Windows are bounded to 31 days; metrics steps must be at least one second and produce at most 11,000 points. query_metrics accepts the equivalent step_seconds argument. Native response JSON and explicit provider outcome states are preserved. Exploration adds bounded metric series and Tempo tags, including truncation indicators, for label cardinality and editor completion.

Insights only advertises Prometheus and Tempo adapters, maintains stable IDs from the full provider namespace/name, and normalizes results for existing widgets. Its API proxy mints a 30-second token for the authenticated human; it never queries as a shared service account. OAuth authorization and refresh also retain exact group membership. See the Insights integration guide.
