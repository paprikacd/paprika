# Paprika v0.3.2

Immutable inline bundles can now participate in native Application promotion.
A publisher declares the logical repository, exact source revision and component
image digests alongside each environment's own immutable manifest ConfigMap.
Paprika verifies upstream release ownership, current health and gates before
creating a target Release with the target environment's own configuration.

Primary application components must deploy their declared digest-pinned images;
a migration Job cannot qualify a substituted API Deployment. Application image
repositories remain pinned in migration and init containers as well. Repository
allow/deny rules apply to inline artifact provenance. Duplicate resource identities
are rejected before apply, including API-version and default-namespace aliases.

Each environment declares the exact manifestHash of its own bundle. Pending
verification and manual approval bind that hash, so deleting/recreating a
same-name immutable ConfigMap cannot substitute tenant settings under old
approval. Explicit hash changes require fresh authorization. Accepted deployment
intent and payload hashes stay frozen while later target bundles wait. Target snapshots can remain Application-owned without creating
workload drift or prune candidates. Workflow Job Pods now receive the existing
pipeline and step labels for network policy selection and inspection.

Existing unversioned inline publishers and Git promotion behavior remain
compatible. Publishers adopting inline artifact metadata must create a new owned
Release and a distinct immutable snapshot instead of editing an old deployment's
provenance. See the [promotion guide](../guides/environment-promotion.md) for the
API contract and external publication flow.

Coverage includes real Kubernetes API admission and controller tests, plus kind
specs for HTTP verification, different tenant domains/configuration, exact image
matching, mismatched revision rejection, sequential publication and accepted
snapshot repair. The focused kind suite also exercises the existing Git dev →
staging → production path across two physical clusters.
